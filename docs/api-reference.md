# API Reference

The authoritative machine-readable contract is `services/api/openapi/act-v1.yaml` (OpenAPI 3.1). This document is a human-oriented index linking each operation to its handler and its test coverage; if the two disagree, the OpenAPI document and the handler code are authoritative, and this file should be corrected.

Every write honours an `Idempotency-Key` header: a retry that re-signs the same event replays the original receipt, while the same key on a different event is `409 idempotency_conflict`.

Request bodies for every write endpoint are DSSE-compatible signed event envelopes (`schemas/envelope/signed-envelope.schema.json` wrapping `schemas/event/unsigned-event.schema.json`), constructed and signed client-side. See `packages/sdk-typescript`'s `buildUnsignedEvent` and `@act/crypto`'s `signEnvelope`. The server never signs on a caller's behalf.

**Tenants.** Every authenticated request acts on exactly one tenant's ledger, named by the verified token's `act_tenant` claim (development scheme: the `x-act-tenant` header; no tenant means `default` unless `ACT_REQUIRE_TENANT` is on, the production default, which refuses the request with `401`). A malformed tenant id is `400 invalid_tenant`, one outside `ACT_TENANTS` is `403 tenant_not_allowed`, and `ACT_MAX_TENANTS` bounds how many exist (`503 tenant_limit_reached`). A signed event must state the caller's tenant in its `tenant` field (`403 tenant_mismatch`; `not_applicable` is refused), except events arriving in a federation bundle, which keep their authoring ledger's tenant. Reading, diffing, tracing or referencing anything that exists only in another tenant behaves exactly as if it did not exist (`404`, or `missing_parent`). `GET /v1/ledger`, peers, the quarantine list, bundle export and every list endpoint are per tenant (ADR 0010).

| Operation | Handler | Auth/trust notes |
| --- | --- | --- |
| `GET /v1/health/live`, `/ready` | `services/api/src/routes/health.ts` | No authentication required |
| `GET /v1/ledger` | `services/api/src/routes/health.ts` | This ledger's public identity (id, receipt-signing key); what a peer operator pins out of band |
| `GET /v1/schemas` | `services/api/src/routes/schemas.ts` | No authentication required |
| `POST /v1/keys` | `services/api/src/routes/keys.ts` | Trust bootstrap: the key id must be the fingerprint of the public key, the actor must own the key, and the key must sign its own registration (ADR 0006, ADR 0009). Administrator-only when `ACT_KEY_REGISTRATION=admin` (production default). Also accepts `key_rotated` / `key_revoked` / `key_compromised` events from a trusted key of the same owner |
| `POST /v1/actors` | `services/api/src/routes/actors.ts` | Requires the signing key already registered via `/v1/keys` |
| `POST /v1/intents` | `services/api/src/routes/intents.ts` | Requires a registered, trusted signing key that belongs to the event's actor and signed the event. `intent_effective_selected` / `intent_merged` additionally require an authority policy (`ACT_AUTHORITY_POLICY_FILE`) that the signers satisfy |
| `POST /v1/transformations` | `services/api/src/routes/transformations.ts` | ditto |
| `POST /v1/artifacts`, `GET /v1/artifacts/{id}`, `GET /v1/artifacts/{id}/versions` | `services/api/src/routes/artifacts.ts` | ditto. The artifact's `version_id` is recomputed and its authoring signature verified. `GET /v1/artifacts/{id}` is computed from lineage: `currentVersionId` is `null` and `conflict` is `true` while competing revisions exist (`tips` lists each); `effectiveVersionId` is the authority-selected baseline |
| `GET /v1/artifacts/{id}/diff?from=&to=` | `services/api/src/routes/artifacts.ts` | Read-only; structural diff (added/removed/changed paths, `services/api/src/diff.ts`) between two versions' artifact-type payloads |
| `POST /v1/approval-requests`, `POST /v1/approval-decisions`, `GET /v1/approvals/{id}` | `services/api/src/routes/approvals.ts` | ditto. The lifecycle of `spec/state-machines.md` section 2 is enforced at write time: a decision needs an existing request for the same subject, must name its own signer as reviewer, and a reviewer decides a request once; only an approved decision can be revoked or expire |
| `POST /v1/challenges`, `GET /v1/challenges` | `services/api/src/routes/challenges.ts` | ditto; `GET` is cursor-paginated like `/v1/events`, pre-filtered to `challenge_raised`/`challenge_resolved` |
| `POST /v1/assignments`, `GET /v1/assignments`, `GET /v1/assignments/{id}` | `services/api/src/routes/assignments.ts` | Accountability assignments (ADR 0011): the source of the roles an authority policy evaluates. A grant needs a tenant administrator, or an active owner of that exact scope who is not granting to themselves (`403 assignment_not_authorized`); it must be recorded by its issuer (`issuer_mismatch`) and name an assignee with a registered key (`unknown_assignee`). Later versions (`revision-of` the latest, `409 not_latest_version`) may only change `status`/`end_time` (`assignment_field_immutable`); `ended` and `revoked` are final (`invalid_assignment_transition`). Assignments imported through a bundle are recorded but confer no role. `GET` is per tenant, filterable by `actor`, `scope` and `active=true` |
| `POST /v1/verifications`, `GET /v1/verifications/{id}` | `services/api/src/routes/verifications.ts` | ditto |
| `POST /v1/policies` | `services/api/src/routes/policies.ts` | ditto |
| `GET /v1/lineage/{id}`, `GET /v1/history/{id}` | `services/api/src/routes/lineage.ts` | Read-only; returns explained findings (missing-parent boundaries, truncation) alongside the raw traversal, via `packages/verification`'s `checkLineageCompleteness` |
| `GET /v1/events` | `services/api/src/routes/events.ts` | `limit` (1-500) and `cursor` are validated strictly (`400 invalid_query_param`). Cursor-paginated (`cursor` = last sequence number); optional `eventType`/`subjectKind` query params filter at the storage layer (`StorageAdapter.queryEvents`), not in memory. Filtering by actor is not supported yet, since actor identity lives inside `envelope_json`, not an indexed column (`docs/roadmap.md`) |
| `POST /v1/bundles/export`, `POST /v1/bundles/import`, `GET /v1/quarantine` | `services/api/src/routes/bundles.ts` | Export computes `completeness` and lists its `known_gaps`. Import and quarantine listing are administrator-only; import verifies the bundle id, its signature against the peer's pinned key, and every source receipt before reading an event, tolerates a missing parent only where the bundle declares the gap, and quarantines (never drops) anything that fails |
| `POST /v1/federation/peers`, `GET /v1/federation/peers`, `DELETE /v1/federation/peers/{peerId}` | `services/api/src/routes/federation.ts` | Administrator-only. Registering a peer is an explicit trust decision that pins its ledger id and signing key; the URL is checked against loopback/private/link-local targets; bearer tokens are stored but never returned |
| `POST /v1/federation/pull`, `POST /v1/federation/push` | `services/api/src/routes/federation.ts` | Real peer-to-peer transport over HTTP: pulls a peer's `/v1/bundles/export` output through the same import path as `/v1/bundles/import` (`services/api/src/bundle-ops.ts`), or pushes this ledger's export to a peer's import endpoint. `pull` also returns `findings.forks` (informational branches) and `findings.equivocations` (adversarial: same reviewer key issuing conflicting decisions over the identical subject+policy) via `@act/ledger`'s `Ledger.findForks`/`findEquivocations`. Neither is a hard reject |

All error responses are RFC 9457 Problem Details (`services/api/src/problem.ts`, `services/api/src/plugins/error-handler.ts`) with a stable `code` field. See the table in `services/api/src/plugins/error-handler.ts`'s `LEDGER_ERROR_STATUS` map for the ledger-originated codes (`schema_invalid`, `digest_mismatch`, `invalid_signature`, `actor_key_not_signer`, `untrusted_actor`, `missing_signature`, `missing_parent`, `duplicate_parent`, `cycle_detected`, `artifact_exists`, `idempotency_conflict`) and `services/api/src/problem.ts` for API-originated ones.

## End-to-End Example

`services/api/src/__tests__/server.test.ts` is the canonical worked example: it registers a key and actor, submits an Intent, records a two-input Transformation, runs a full approval-request/decision/challenge/verification/policy cycle, paginates events, and exports and imports a bundle into a second independent ledger, all against the real handlers, not mocks.
